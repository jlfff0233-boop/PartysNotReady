# GUIDELINE

## PURPOSE

Rabbit Party 프로젝트에서 반복해서 적용할 작업 방식, 협업, 코드 작성, 구현, 메모 관리 규칙을 관리합니다. 게임 기능의 상세 기획은 `DECISION.md` 또는 `System` 문서에서 관리합니다.

## WORK_START

1. GUIDELINE과 TODO의 현재 작업을 확인합니다. 같은 대화에서 이미 읽은 규칙은 변경이 없으면 다시 읽지 않습니다.
2. 해당 작업의 System 문서에서 관련 절만 조회합니다. 파일명과 제목 검색으로 범위를 먼저 좁힙니다.
3. 전역 결정은 DECISION, 확인 이력은 DONE, 오류 원인은 ERROR가 필요할 때만 조회합니다. ROADMAP은 전체 단계 변경 시 확인합니다.
4. 관계없는 문서와 전체 이력을 매 작업마다 읽지 않습니다.
5. 코드 작성 전 변경 대상 전체와 같은 기능 / 역할의 참고 스크립트를 읽습니다. 이름 검색이나 일부 선언 확인만으로 스타일을 파악했다고 판단하지 않습니다. 구체적인 확인 절차는 아래 SCRIPT_REFERENCE_WORKFLOW를 따릅니다.

## COMMUNICATION

- 작업 문서는 기능 단위의 현재 상태와 다음 행동만 간결하게 기록합니다. 개별 객체의 설정 이력, 반복 로그, 조사 경과와 폐기한 추측은 제외합니다. 검증은 확인 완료 / 코드 반영·실행 미확인 / 미해결로 구분하고 핵심 한 줄로 요약합니다.

- 존댓말을 사용하고 설명은 최소화하며 코드 중심으로 답변합니다.
- 정보가 부족하거나 확인되지 않은 내용은 추측하지 않고 사용자에게 확인합니다.
- 수정 후에는 변경 사항과 검증 여부를 요약해 보고합니다.
- 큰 작업 묶음 완료 보고에는 실제 수정 파일 전체 목록 / 파일별 변경 1~2줄 / public API / SerializeField 변경 / Inspector 수동 연결 / 삭제 / Rename / Move 여부 / 게임플레이 차이 / 정적 검증 / Unity 플레이 / 빌드 미확인을 함께 기록합니다. 전체 코드는 붙이지 않습니다.
- 코드 구현 / 인스펙터 설정과 연결 / 실행 검증을 별도 단계로 구분하여 설명합니다. 추가 코드가 필요 없는 설정이나 검증을 남은 구현으로 안내하지 않습니다.
- 코드와 문서는 최초 수정부터 apply_patch로 편집합니다. 사용자가 요구하는 UI는 `○○을 편집했습니다` 파일별 변경사항 박스와 검토 패널 두 가지입니다. 수정 완료 후 검토 패널도 열기를 요청하며, 표 / 코드 블록 / 전체 미커밋 리뷰로 변경사항 박스를 대체하지 않습니다.
- 변경사항 박스를 표시하려고 이미 수정한 파일을 되돌렸다 재적용하지 않습니다. 파일 직접 쓰기로 최초 패치를 우회하지 않으며 기존 인코딩과 줄바꿈을 보존합니다.
- 기존 파일은 실제로 바뀌는 줄과 위치 식별에 필요한 최소 주변 문맥만 포함한 부분 패치로 수정합니다. 여러 곳을 수정할 때도 변경 지점별로 패치를 나눕니다.
- 일부 내용만 수정하면서 파일 전체 또는 첫 줄을 제외한 본문 전체를 삭제 후 다시 추가하는 패치는 금지합니다. apply_patch를 사용했더라도 변경사항 박스가 전체 수정으로 표시되어 사용자가 실제 변경 위치를 확인하기 어렵다면 올바른 수정 방식이 아닙니다.
- 변경 없는 후속 답변에서 last-turn을 호출해 이전 수정의 변경사항 박스를 다시 열 수 있다고 안내하지 않습니다. 표시 여부를 확인하지 못했으면 열었다고 보고하지 않습니다.
- 구조 / API 변경 또는 버그 수정 시 기존 코드와 수정 코드의 핵심 차이를 2줄 이내로 설명합니다.
- 발생 가능한 사이드 이펙트가 있으면 `Warning`으로 명시합니다.

## CODE_STYLE

- 프로젝트 코딩 기준은 이 문서에서 관리하며 충돌한 규칙은 교체합니다. 기존 파일 형식 / 인코딩 / 줄 바꿈과 사용자 최신 이름 / 구획을 우선합니다. 신규 Markdown은 BOM 있는 UTF-8입니다.
- XML summary는 여는 태그 / 내용 / 닫는 태그를 별도 줄로, param / returns는 한 줄로 작성합니다. 필드는 짧은 한글 설명을 작성하고 // 뒤에는 공백을 넣지 않습니다. 설명 간격은 가까운 참고 코드에 맞추며 탭 수를 고정하지 않습니다. 컬렉션은 원소 / Key / Value 의미가 드러나도록 설명하고 필요하면 summary를 사용합니다.
- 멤버 → 초기화 / 구독 → 프레임 진행 → 핸들 → 기능 → 공통 검사 / 조회 순으로 배치합니다. 기능 전용 조회 / 검사 / 계산은 해당 기능 하단에 둡니다. 짧은 프로퍼티는 expression body를 허용하며 일반 함수의 기존 expression body를 형식만으로 일괄 변환하지 않습니다. Rename / 접근 범위 / 한정자 변경은 승인 범위만 적용합니다.
- 긴 책임 흐름은 `#region ----- 기능명 -----`으로 묶되 함수 한두 개나 짧은 Unity 호출을 위해 나누지 않습니다. 연속 행동은 같은 구획으로 두고 필요하면 통합 / 생략합니다. 구획 이름은 실제 역할인 핸들 / 디버그 등을 사용합니다.
- region / endregion 위아래는 빈 줄 한 줄, 필드 / 프로퍼티 / 이벤트나 Unity 호출 바로 다음 region 위는 두 줄입니다. Init / Awake / 활성화 / 구독 흐름이 길면 초기화 구획으로 묶고 Start / Update / LateUpdate는 책임에 따라 별도 배치합니다. OnDisable은 클래스 하단 배치 기준을 따릅니다.
- Inspector 참조와 설정은 공통 컴포넌트 / 실제 기능별 Header와 빈 줄로, 런타임 필드는 수명 / 용도별로 묶습니다. 공백 / 괄호 / 줄 나눔과 미리보기 코드도 참고 스크립트 형식을 따릅니다.
- bool 조건은 `== true` / `== false`로 명시하되 반환 / 대입까지 비교식으로 바꾸지 않습니다. 긴 조건 프로퍼티는 검사 함수를 사용합니다.
- 필드에는 짧은 한글 설명을 작성합니다. enum과 의미가 바로 드러나지 않는 지역 변수에도 필요한 설명을 작성하며 기존의 적절한 설명은 유지합니다. 자명한 반복 인덱스 설명은 생략하고 비트 연산이나 실행 순서에는 의도 주석을 추가합니다.
- 이름 / 설명 / 주석 / 배치를 함께 정리하되 스타일 변경에 게임플레이 변경을 섞지 않습니다. 기존의 적절한 설명과 사용자 구획을 보존하고 완료 후 문서 / 코드 차이를 다음 작업에도 적용합니다.
- 변경 설명 / 미확정 정책은 코드 밖에 작성합니다. 승인 대기를 TODO 주석으로 대체하거나 구현 대화를 남기지 않습니다.
- 별도 스타일이 없으면 구현 전에 기준을 확인합니다. 가독성 / 유지보수성 / 보안 / 성능을 우선합니다.

### SCRIPT_REFERENCE_WORKFLOW

1. 수정할 파일 전체를 읽고 최신 사용자 수정의 이름 / 용어 / 멤버 배치 / region / 주석 / 공백 형식을 확인합니다. 기존 동작과 수명 계약도 함께 확인합니다.
2. 신규 클래스나 기존 파일에 없는 형태를 작성할 때는 같은 기능 또는 역할의 스크립트를 참고합니다. 변칙 / 아이템 / 제작 / Editor 등 작업과 가까운 코드를 선택하고 최근 사용자 정리본을 우선합니다. 참고 파일을 실제로 읽고 선택한 경로를 작업 보고에 간단히 밝힙니다.
3. 과거 코드나 다른 기능의 스타일을 섞어 사용자의 최신 정리를 되돌리지 않습니다. 명시 규칙과 실제 코드가 충돌하면 사용자 최신 지시를 먼저 확인하고, 해소되지 않는 부분만 질문합니다. 충돌을 이유로 승인 범위 밖 파일 전체를 정리하지 않습니다.
4. 수정 후 기능 검증과 별도로 변경 부분을 참고 코드와 대조합니다. Summary / param / returns, enum·필드·지역 변수 설명, Header / region, bool 조건, 기존 용어, 한자 혼입, 불필요한 Rename과 장황한 주석을 확인합니다.
5. 완료 보고에 실제 수정 파일과 필드 / 함수별 변경, 확인한 범위와 남은 수동 작업을 구분합니다. 사용자 수정 사항을 확인했다는 말만 남기지 않고 다음 코드 작성에도 같은 기준을 적용합니다.

### VALIDATION_AND_CLEANUP_STYLE

- Inspector에서 연결하는 필수 참조마다 null 검사 / 오류 로그를 일괄 추가하지 않습니다. 설정 데이터 검증과 실제 초기화 실패 / 선택 기능 / 파괴 경계의 검사를 구분하고 하위 기능이 보장한 계약을 반복 검사하지 않습니다.
- 검사는 실제 입력 / 게임 규칙 / 객체 수명에 필요한 경우에만 작성합니다. 상위에서 보장한 검사를 반복하거나 미래 상황을 위한 요청 큐 / 재진입 플래그를 관성적으로 추가하지 않습니다.
- 처리 중 플래그나 획득한 임시 상태는 예외와 조기 반환에서도 해제되도록 합니다. 해당 수명을 보장하는 `try/finally`를 단순해 보인다는 이유로 수동 해제로 바꾸지 않습니다.
- 여러 작업을 무조건 이어 가기 위한 중첩 try/finally와 부모 / 자식의 중복 정리를 지양합니다. 구체적인 상태 / 자원 수명을 보장하는 최소 범위의 정리는 유지합니다.
- 예외를 숨기기 위한 포괄적인 catch나 성공처럼 진행하는 대체 동작을 추가하지 않습니다. 필요한 복원은 해당 상태 소유자가 담당하고 호출 관계를 장황한 주석으로 반복하지 않습니다.

### SCRIPT_NAMING_AND_SUMMARY

- 새 GameObject와 개발 도구 메뉴의 이름 / 경로는 영문을 사용합니다. 예: Visual / Body / RestoreArea, Tools/MapChecks/Presence. 한글 Summary / 설명 작성과 이름을 구분합니다. 기존 씬 / 프리팹 객체의 Rename을 코드 수정에 자동 포함하지 않으며 사용자 수정과 직렬화 참조를 보존합니다.

- 코드 / Summary / 주석 / region에서 기존 프로젝트에 없는 도메인 용어를 임의로 만들지 않습니다. 기존 코드 / 문서의 용어를 우선하고 같은 개념에 새 동의어를 추가하지 않습니다. 제작에서는 `등록`, `등록 해제`, `제작 대상`, `그릇`, `제작`을 우선하며, 새 용어가 필요하면 먼저 제안합니다.

- 스크립트 파일명과 클래스명을 일치시킵니다. 이름은 실제 책임을 기준으로 정하며 MonoBehaviour 상속 여부로 역할을 구분하지 않습니다.
- UI 전체의 대상 연결 / 화면 전환은 `Hud`, 그 아래 특정 화면의 표시 / 입력은 `Panel`로 구분합니다. 하위 화면마다 `Hud`를 반복하지 않습니다.
- 문맥과 타입으로 역할이 분명하면 `_recipe`, `_minigame`, `_prevButton`처럼 짧게 씁니다. 구별에 필요한 단어까지 생략하거나 기존 이름을 일괄 축약하지 않습니다.
- View / Presenter / Model 등의 아키텍처 접미사를 일관성만을 이유로 강박적으로 붙이지 않습니다. 클래스의 실제 책임과 역할이 이름에서 가장 잘 드러나는 표현을 우선하며, 아키텍처 역할을 명시할 필요가 있을 때만 해당 접미사를 사용합니다. 단순 기능 모듈은 CharacterSound / ItemSound / ProductionSound처럼 기능 이름을 사용해도 됩니다. 기존 클래스의 일괄 Rename은 별도 요청 범위입니다.
- 실행 모듈은 `Mover`처럼 동작을 나타내는 이름을 사용합니다. `ItemHold`, `ItemPhysics`, `ItemPlacement`처럼 기능이 명확한 이름도 허용하며 모든 모듈에 억지로 `-er`를 붙이지 않습니다.
- 검사 전용 클래스는 `기능명Checker`로 명명합니다. 예: `PresenceSpaceChecker`. 이름이 비슷하다는 이유만으로 다른 책임의 기능을 합치지 않습니다.
- 클래스 서머리는 생성자 동작이 아니라 클래스 전체 책임을 짧은 한글 역할로 작성합니다. `명칭 - 담당 기능` 형식을 기본으로 사용합니다. 예: `이동 모듈 - 이동, 점프` / `탐색 모델 - 가까운 유효 대상 선정` / `포획 중재 - 대상 확보, 해제, 결과 전달` / `등장 공간 검사 - 다른 물체와 겹침 확인`.
- 함수 서머리는 실제 행동을 짧고 직접적으로 적고, 프로퍼티는 나타내는 상태를 적습니다. 예: `공간이 비어 있으면 물건 표시` / `대상 표시 여부`. 추상적인 표현이나 클래스 책임 설명을 반복하지 않습니다.
- 필드 설명과 내부 주석은 이름 / 타입으로 알 수 있는 내용을 길게 반복하지 않습니다. 표시 / 입력 가능 / 객체 활성화 / 연결 해제를 구분하고, 코드가 직접 하지 않는 일을 설명하지 않습니다. 컬렉션은 저장하는 대상과 Key / Value 의미를 설명하며 구현 순서를 적지 않습니다.
- `Try`는 실패할 수 있는 실행 요청이나 결과 획득에 사용하며 bool 반환만으로 붙이지 않습니다. `Handle`은 수신한 입력 / 이벤트를 처리하는 함수에 사용합니다.
- 공용 스크립트의 서머리와 주석은 실제 역할을 설명하며, 현재 사용하는 특정 기능으로 범위를 한정하지 않습니다.
- 변칙 사건의 기능 명칭은 서머리에서도 유지합니다. `개폐 변칙 사건`, `대체 변칙 사건` 등을 임의로 `개폐 사건`, `대체 사건`으로 줄이지 않습니다.
- Unity 호출 함수 자체의 summary는 필수가 아닙니다. 함수 내부 코드의 의도와 초기화 / 구독 / 해제 등 처리 순서에 필요한 주석을 우선합니다. 일반 클래스 / 함수의 한글 summary와 매개변수 설명 규칙은 유지합니다.
- 코드 주석 / 서머리의 병렬 기능은 쉼표 또는 양쪽 공백 없는 `/`로 구분하며 가운뎃점을 사용하지 않습니다. 이 규칙만으로 기존 Markdown 본문의 문장부호를 일괄 치환하지 않습니다.
- 기존 이름을 프로젝트 전체에 일괄 적용하는 작업은 별도 요청 범위로 다룹니다. Unity 파일명 변경은 사용자가 프로젝트 창에서 진행하고, 클래스명 / 생성자 / 참조 코드를 함께 맞춥니다. 직렬화 필드명은 클래스명 변경만을 이유로 바꾸지 않습니다.

- 매개변수가 있는 함수는 out / ref를 포함해 각 매개변수의 한글 `<param>`을 작성합니다. 반환값이 있는 일반 함수는 `<returns>`를 작성합니다. 설명은 짧게 쓰되 시도 ID / 목표 ID, 검사 / 실행, 판정 결과 / 최종 제작 결과를 구분합니다.
- Unity Message 함수는 초기화 / 구독 / 프레임 진행 책임으로 배치하되 OnDisable은 클래스 하단에, 기즈모 함수가 있으면 그 아래 최하단에 둡니다. 기존 파일 전체를 배치 통일만으로 재정렬하지 않습니다.
- 일반 함수와 필드의 `private`은 생략하되, private Unity 호출 함수에는 명시합니다. 상속을 위한 protected / override 선언은 유지하며 사용자가 정한 변수명과 필드명을 임의로 변경하지 않습니다.

- sealed / readonly / internal / static은 습관적으로 추가하거나 유지하지 않습니다. 상속 제한 / 불변 참조 / 접근 경계 / 공유 책임의 실제 근거와 호출부 영향을 확인합니다. 승인되지 않은 제거 후보는 별도로 보고합니다.
- 일반 호출의 ?.는 선택 참조 / 초기화 전 / 실패 정리 / 파괴 시점의 수명 계약을 확인합니다. 필수 참조 오류를 숨기지 않되 실제 null 가능 경계의 검사는 유지합니다. Unity 파괴 객체는 Unity null 비교로 검사하고 이벤트의 ?.Invoke()는 유지합니다.
- 스타일 완료는 형식뿐 아니라 설명과 실행의 의미 일치, 승인된 후보 반영, 전체 호출부 / 문자열 / 직렬화 영향 확인을 포함합니다. 미적용 코드 항목이 남으면 전체 완료로 보고하지 않습니다. Unity 수동 연결 / 파일 Rename / 실행 검증은 코드 반영과 구분해 보고합니다.

## IMPLEMENTATION

- 주요 언어는 C#, 엔진은 Unity 6 `6000.0.68f1`을 기준으로 합니다.
- C# 빌드와 Unity 직접 빌드는 지양하며, 사용자가 요청하거나 꼭 필요한 경우에만 수행합니다.
- 정적 검증은 수정 파일과 직접 호출 / 이벤트 구독 / 직렬화 / 상속 / 인터페이스 / 변경 API 의존성을 기본 범위로 합니다. 필요한 경우에만 인접 의존성으로 넓히고 검사 파일과 범위 선정 이유를 보고합니다.
- 프로젝트 전체 Editor / Player Roslyn 검사는 대규모 Rename, 공통 인터페이스 / 기반 타입 변경, 시스템 간 API 변경, 최종 교차 감사 또는 국소 검사로 원인을 찾지 못한 컴파일 오류에 한정합니다. 주석 / 스타일 / 개별 책임 분리만으로 매번 전체 소스를 검사하지 않습니다.
- 씬, 프리팹, Unity YAML 및 `.meta` 파일을 직접 생성 / 수정 / 삭제하지 않습니다.
- 실제 확인하지 않은 기능을 구현 완료로 보고하지 않습니다.
- 작업 트리의 기존 변경을 보존하고 요청 범위 밖의 파일은 수정하지 않습니다.
- 계획 설명 / 코드 미리보기 / 질문 답변은 파일 수정 허가가 아닙니다. 문서도 갱신 요청이 있을 때만 수정합니다.

## TERMINOLOGY

- 프로젝트 공식명은 `Rabbit Party`로 사용합니다.
- `Preparation`은 현재 실제로 유효한 파티 준비 상태, `Safety`는 초대 토끼의 안전, `Mood`는 손님의 즐거움과 편안함, `Predator Control`은 포식자 대응 성과를 뜻합니다. 음식 탈취나 배치 이탈로 달라진 상태는 Preparation에 반영하며 Mission 달성 이력과 구분합니다.
- `NPC 토끼`는 파티에 초대된 손님을 뜻하며 플레이어 캐릭터와 구분합니다.
- `포식자`는 파티 준비를 방해하는 위협의 공통 명칭입니다.

## DOCUMENT_DIAGRAMS

- 시스템 구조는 Mermaid 구조도, 전환 조건은 상태도, 호출 순서는 시퀀스로 구분합니다. 구조도의 실선은 소유 / 요청 / 데이터 전달, 점선은 이벤트 알림이며 연결선에 의미를 표시합니다. 후속 설계는 현재 구현과 별도 그림에 명시합니다.
- 전체 시스템 경계는 DECISION, 상세 실행 / 실패 / 취소 계약은 담당 System 문서에 둡니다. 도식 추가만으로 구현 / 실행 검증 완료를 기록하지 않습니다.

## MEMO_RULE

- 전역 확정 기획은 `DECISION.md`, 시스템별 상세 확정 / 미정 사항은 `System` 문서를 단일 원본으로 사용합니다.
- 현재 우선순위는 `TODO.md`, 전체 단계는 `ROADMAP.md`, 실제 구현 완료는 `DONE.md`에서만 관리합니다.
- 실제 진행을 막고 원인 추적에 시간이 걸린 오류만 `ERROR.md`에 기록합니다.
- 임시 인수인계가 필요할 때만 `HANDOFF.md`를 생성하며 영구 단일 원본으로 사용하지 않습니다.
- 동일 내용을 여러 문서에 중복 기록하지 않습니다.
- 저장소 문서에는 개인 PC의 절대 경로나 외부 다운로드 파일 의존성을 남기지 않습니다. 파일 참조는 저장소 내부 상대 경로를 사용합니다.
- 짧고 같은 성격의 항목은 `/`로 묶습니다.

- 메모에는 현재 계약 / 확정 계획 / 남은 결정 / 확인 결과만 기록합니다. 대화 과정, 작업 장소, 에이전트 작업 보고와 폐기된 제안은 넣지 않습니다.
- 상태는 코드 반영 / 사용자 확인 / 미확인으로 짧게 구분합니다. 동일 규칙과 확인 목록은 담당 문서 한 곳에 두고 다른 문서는 링크로 연결합니다.
- ERROR는 향후 문서 작성의 근거 자료이므로 축약 대상에서 제외합니다. 증상 / 재현 조건 / 원인과 근거 / 조치 / 확인 범위와 미확정 사항을 상세히 보존합니다.
