# ERROR

## PURPOSE

개발 진행을 실제로 막았고 원인 추적에 시간이 걸린 오류와 해결법을 기록합니다. 반복적인 조작 불편으로 입력 방식을 변경한 경우에는 증상과 개선 이유도 짧게 남깁니다. 단순 경고 / 미구현 기능 / 일반 설계 고민은 기록하지 않습니다.

- 초기 증상: 여우가 길을 찾는 동안 방향을 반복 변경하다가 벽을 통과해 현관으로 바로 이동하는 것으로 보고됐습니다. 이후에는 좁은 구간의 토끼 / 가구에 막혀 떨림, 이동 정체 재시도와 전체 제한시간 초과가 함께 보고됐습니다.
- 확인된 배경: 앞선 공격 / 포획 수정 후 사용자가 포획 성공을 확인했습니다. 파티룸과 현관이 가까워 구조 전에 납치가 끝나는 문제가 보고돼 자동 우회 방식을 선택했습니다. 가까운 배치는 구조 시간 확보의 문제이며 벽 관통의 확정 원인은 아닙니다.

### 재료 구성 오류의 반환 무한 대기

2026-09-30 정적 검토에서 확인한 실패 경로입니다. 초기 구성 검사 코드를 반영했으며, 해당 실패 상황의 Unity 재현은 미확인입니다.

- 조건 / 원인: 콜라이더 등 필수 구성이 빠진 재료도 공급원 초기화의 데이터 / 반환 핸들러 검사는 통과할 수 있습니다. 미리 생성한 재료는 DontDestroyOnLoad에 있어 플레이 씬 아이템 검사에서 제외됩니다. 첫 대여 준비 실패 후 반환 대기로 보내지만 반환도 같은 구성 검사에서 실패하여 계속 남고, 씬 이동까지 막습니다.
- 반영 범위: `ItemWorldController.GetCollider`를 초기화와 구성 검사에서 공유하고, `CheckConfiguration`에서 Collider / Rigidbody 존재 여부를 검사합니다. `IngredientSource.Init`은 풀 등록 / 생성 전에 프리팹을 검사하고 누락된 필수 구성과 공급원 / 프리팹을 보고한 뒤 실패합니다.
- 처리 방식: 잘못된 프리팹이 풀에 들어가기 전에 초기 준비를 중단합니다. 구성 검사에서 초기화나 대체 컴포넌트 추가는 수행하지 않습니다. 기존 대여 / 반환 준비, 재고의 반환 대기 / 종료 처리와 소비 중 일시적인 반환 대기는 유지합니다.
- 완료 기준: 잘못된 프리팹을 시작 시 식별하고, 실패 정리 후 영구 반환 대기나 씬 이동 차단이 남지 않아야 합니다. 정상 재료의 소비 / 재대여도 유지합니다.
- 확인 범위: 사용자 코드 검토와 정적 검사 완료. 위 완료 기준의 Unity 실행 확인은 남아 있습니다.


### 변칙 사건 방치 후 적 미등장

- 증상: 사건을 방치해도 적 활동으로 이어지지 않음. 여우 보복 컨텍스트 테스트는 방 활동이 시작되지 않았다는 경고로 중단됨.
- 조사 당시 Spawn SO에 이전 `_enemyTypes` 배열이 남아 있고 현재 코드의 `_enemyType` 값은 None으로 읽히는 구성을 확인. None은 독립 사건 경로이므로 적의 AnomalyLinker와 연결되지 않음.
- 조치: 통합 디버그에 실제 EnemyType / 적 / 사건 등록 진단과 시작 불가 사유를 추가. 여우 컨텍스트 테스트는 공통 방 활동 준비를 거치도록 수정. SO는 자동 수정하지 않음. 이후 사용자 로그에서 사건 실패 전달 → 여우 추격·공격 / 담비 수집을 확인.
- 곰 음식 전달도 SpawnDataMap의 Demand 그룹 누락으로 활동 시작이 거절되던 설정 문제였음. 사용자 등록 후 싫어하는 음식 난동 / 좋아하는 음식 퇴장을 확인. 재료 카테고리를 제외하는 코드 문제는 아님.
- 별도: 함께 보고된 DontSaveInEditor Assertion은 GUIUtility 호출 정보만으로 원인을 특정하지 못했으며 해결 완료로 취급하지 않음.

### 레시피 자동 표시와 연속 재료 배치 불편

- 증상: 재료를 배치할 때마다 커서 잠금이 자동 해제되어 시점 조작과 다음 재료 배치 흐름이 끊겼습니다.
- 개선 과정: 거리 감지로 레시피 패널을 자동으로 열고 닫도록 변경했지만, 배치 시 커서 잠금이 풀리는 불편은 남았습니다. 재료 상호작용 분리와 별도 상호작용 키도 시도했으나 키를 추가로 사용하는 조작 역시 불편했습니다.
- 최종 조치: 필요한 재료를 연속 배치한 뒤 F로 레시피를 선택적으로 열어 확인 / 조리하도록 변경했습니다. 접근 / 재료 배치 자체는 패널과 커서를 변경하지 않습니다. 현재 입력 계약은 [레시피 입력](System/PLAYER_INTERACTION.md#recipe_interaction_plan)을 따릅니다.
- 확인 범위: 사용자 설명에 근거한 개선 경위입니다. 중간 구현의 정확한 키 / 함수 / 세부 순서는 확인되지 않아 특정하지 않습니다. 최종 레시피 사용과 안내 표시는 사용자 확인입니다.

### 실패 후 조리 버튼 비활성 유지

### TableItem 낙하 후 보유 중 부양과 지지 표면 진단

- 증상 / 재현: 낙하 후 TableItem을 집어 바닥에 가까이 대면 플레이어가 뜨거나 밀림. 종료 후 바닥의 대상으로 재발생 시 지지 표면 오류 표시.
- 로그 근거: TableItem은 Ready → Active → Failed → Expired 한 건이며 반복 발생 기록 없음. 보유 중 반복 낙하로 단정할 수 없었음.
- 원인: Books I의 대표 BoxCollider 외 자식 MeshCollider 5개가 있었으나 ItemHold는 대표 하나만 비활성화. HoldItem 물리 충돌도 허용되어 자식 충돌이 남았음.
- 조치: 같은 Rigidbody의 Collider 자동 수집 / 개별 활성 상태 저장 / View 보유 중 전체 비활성화 / 해제 시 복원. 별도 Rigidbody 제외, World 보유자 충돌 제외도 전체에 적용.
- 표면 원인: 실제 표면 조회와 정상 배치 표면 일치 검사가 결합되어 불일치도 SupportMissing으로 보고됨.
- 표면 조치: 조회 분리, 실제 바닥 접촉 우선, 표면 없음과 불일치 구분. 정상 배치 기준 유지.
- 확인: 복수 Collider / 원래 비활성 / 별도 Rigidbody / World → View 전달 / 재수집 로직과 구문 검사 수행. 사용자 수정 후 문제 해결 보고. 모든 형상과 Unity 물리 예외 자동 재현은 아님.

### 2026-09-18 Presence 초기 표시 설정 검사와 초기화 순서

- 증상: PresenceController.Awake에서 “존재 기능의 초기 표시 설정을 확인해 주세요.” 오류 발생. 사용자가 Initially Present를 켜거나 끄고 Renderer 활성 상태를 맞춰도 오류가 지속됐다고 보고.
- 원인과 근거: 초기화 시 필요한 참조 / 설정 검사와 초기화 완료 후의 실행 준비 검사가 섞여 있었음. Awake 시점에 View의 초기화 완료나 활성 준비 상태를 전제로 검사하면 Inspector의 초기 표시 값을 바꾸는 것만으로 해결되지 않음. 단순 체크값 불일치로 모든 보고를 설명하지 않음.
- 조치: Presenter가 View.TryInitialize에 초기 표시 값을 전달하고 적용 성공 후 같은 값으로 Model 생성. View의 설정 검사와 초기화 후 상태 검사를 구분하고, 실패 시 대상 이름과 구체적인 사유를 출력. Collider의 정상 활성 상태와 복구 대기 중 비활성 상태도 구분해 검사.
- 확인 범위: 이후 복구용 제거와 조사 후 재등장, Remove 사건과 적 연계의 기본 동작을 사용자 확인. 과거 모든 초기화 조합이나 실행 순서 변형을 재현 검증한 것은 아님.
- 재발 방지: Awake에서 초기화 완료 후 전용 준비 조건을 초기화의 선행 조건으로 사용하지 않음. 초기 표시의 기준은 Presenter 설정 한 곳이며 Renderer / 자식 활성 상태를 수동으로 맞추는 절차에 의존하지 않음.

### 2026-09-17 ShowHide 숨김 중 부모 Rigidbody 낙하

- 증상: ShowHide 구성에 ItemWorldController / Rigidbody를 둔 대상이 시작 직후 또는 숨김 중 바닥을 관통해 계속 떨어진다고 사용자 보고.
- 재현 조건과 근거: 저장된 Item (1)의 부모 Rigidbody는 Use Gravity 활성 / Is Kinematic 비활성이며 유일한 Collider는 숨기는 Renderer 자식에 있었음. 자식을 비활성화하면 충돌체만 사라지고 부모의 중력은 계속 적용되는 구조임. 보고된 모든 시작 직후 낙하가 동일 경로였다고 단정하지 않음.
- 관련 설정: ItemWorldController는 RequireComponent로 Rigidbody를 요구하지만 ShowHide 조사에는 ItemWorldController가 필수가 아님. 비운반 장식에는 Rigidbody 없이 표시와 조사 기능만 사용할 수 있음.
- 조치: ItemPhysics.SetHidden이 숨기기 전 중력 / Kinematic 설정을 저장하고 속도를 제거해 물리를 정지. ShowHideView는 처음부터 숨겨진 대상도 초기화 때 정지시키고, 자식 표시 후 기존 물리 설정을 복원. ItemWorldController가 있으면 GetPhysics로 같은 모듈을 공유하며 초기 Collider 조회는 비활성 자식까지 포함함. 루트 Rigidbody만 있는 경우에도 물리 모듈을 연결함.
- 충돌 방지: 숨김 중 SetVelocity / SetPlacementPhysics / ApplyImpulse 적용 차단. 보유 중에는 ShowHideModel이 등장 / 제거 / 조사를 거절하며 Presenter가 ItemCarry.IsHold를 전달함. View는 보유 허용 여부를 판정하지 않음.
- 확인 범위와 남은 확인: 코드 반영 상태. 숨김 중 위치 유지, 재등장 시 원래 중력 / Kinematic 복원, 반복 등장 / 제거, 보유 제한의 실제 플레이 결과는 아직 확인되지 않음. 재등장 시 숨기기 전 이동 / 회전 속도는 복원하지 않으며, 기존 고정 아이템을 무조건 동적 Rigidbody로 바꾸지 않음.
- 재발 방지: 표시와 함께 Collider를 끄는 기능은 활성 관리 루트의 물리 수명을 함께 처리해야 함. 정상 아이템의 낙하 / 투척을 유지해야 하므로 Rigidbody를 일괄 제거하거나 항상 Kinematic으로 고정하는 방식으로 해결하지 않음.
