# DECISION

## PURPOSE

Rabbit Party 프로젝트 전체에 공통으로 적용되는 확정 기획, 구조, 범위와 시스템 책임 경계를 관리합니다.

## CURRENT_DECISION

### 게임 콘셉트

- 3D 협동 파티 준비 게임으로, 플레이어는 업무 중 침입한 포식자를 발견하고 포식자별 규칙에 맞게 대응합니다.
- 엔진은 Unity 6, 중심 경험은 멀티 협동이며 싱글플레이도 고려합니다.
- 개발 기간은 약 1~2개월, 맵은 하나의 시설 안에 조리실 / 창고 / 파티룸 / 드레스룸을 둡니다.
- 공식 최종 목적은 포식자 처치가 아니라 제한 시간 안에 파티를 충분히 완성하는 것입니다.
- 좋은 플레이는 파티 준비 / 손님 보호 / 분위기 유지 / 포식자 대응 / 피해 복구의 균형으로 평가합니다.

### 핵심 게임 루프

`파티 준비 업무 선택 → 업무 수행 → 이상 징후 또는 포식자 이벤트 → 상황 판단 → 고유 규칙 대응 → 피해 복구 → 업무 복귀`

### 공통 구성 요소

- 핵심 공간: 조리실 / 창고 / 파티룸 / 드레스룸
- 핵심 업무: 조리 / 물건 찾기 / 운반 / 배치 / 음악 관리 / 의상 준비
- NPC 토끼: 약 8마리, 싱글·멀티 공통 등장
- 기본 포식자 후보는 개 / 곰 / 까마귀 / 담비 / 여우입니다. 변장 적은 담비와 별개의 너구리 계열 Enemy로 후순위 확장합니다.
- 평가축: Preparation / Safety / Mood / Predator Control
- 초기 시스템 구현은 최종 동물 모델보다 더미 모델을 우선 사용합니다.
- 게임 진행과 단계형 미션은 [GAMEPLAY_CYCLE](System/GAMEPLAY_CYCLE.md)을 따릅니다. 미션 달성 이력과 현재 준비 점수를 분리하며, 음식 제작과 파티룸 꾸미기를 핵심 목표로 우선합니다. 의상은 선택 / 보너스 후보로 재검토합니다.

### 레시피 진입 결정

- 레시피는 조준 후 F로 명시적으로 열고 닫는 방식으로 변경합니다. 거리 자동 열기와 재료 배치 후 커서 해제가 이동 / 연속 작업 / 다른 상호작용을 방해한 사용자 확인을 반영합니다.
- 구조 F 입력은 한곳에서 분기하며 자신의 탈출 우선순위를 보존합니다. 상세 규칙은 [레시피 상호작용](System/PLAYER_INTERACTION.md#recipe_interaction_plan), 남은 작업은 [TODO](TODO.md#recipe_interaction_fix)를 따릅니다.

## ARCHITECTURE_PATTERN

- 구조 변경은 확정된 게임플레이 / 계약 보존 → 실제 역할에 맞는 책임 → 상태 / 분기 중복 제거 → 더 작은 구조 → 현재 클래스 경계 유지의 이득 → 미래 확장용 과설계 여부 순으로 판단합니다. 현재 클래스 구조를 덜 바꾸는 것 자체는 개선 기준이 아닙니다.
- 현재 복잡도를 줄이는 전용 실행 객체 / 클래스 분리 / 책임 이전은 허용 후보입니다. 새로운 MERGE / SPLIT / 책임 이전 / 클래스 / 추상화 / API 구조 변경은 구체 범위를 제안하고 사용자 승인 후 적용합니다. 실제 책임과 사용 근거 없이 미래 확장만을 위한 범용 Service / Coordinator / Framework는 만들지 않습니다. 이전 작업 가이드와 감사의 구조 보존 / 새 계층 금지는 이 기준으로 정정합니다.
- 프로젝트 전반에 MVP 책임 분리와 기능별 모듈화를 고려하되 모든 기능을 Model / View / Presenter 세 클래스로 나누지는 않습니다.
- TargetSearcher처럼 책임이 명확하고 함께 동작하는 기능은 하나의 클래스로 구성할 수 있습니다. 분리 / 통합은 클래스 수나 줄 수보다 책임, 변경 이유, 재사용 범위로 판단합니다.
- Data는 조정용 설정값을 보관하는 ScriptableObject로 분리하며 런타임 상태는 저장하지 않습니다. 적별 Data를 우선하고 공통 설정 계층은 실제 중복이 반복될 때 추출합니다.
- Model은 게임 규칙과 판단에 필요한 런타임 상태를 소유하며 월드 표시 / 물리 적용은 소유하지 않습니다. EnemyRoomModel의 현재 방과 방별 이력처럼 규칙 식별에 필요한 참조와 Transform / GameObject의 직접 적용을 구분합니다.
- Presenter는 씬 참조와 Model / View / Module 연결, 실행 순서를 관리합니다. 세부 기능은 Module에 위임하고 View는 Model을 직접 조작하지 않습니다.
- Module은 독립 기능과 내부 상태를 소유합니다. State는 상태 전용 진행 정보를 소유하되 경로 갱신 타이머처럼 Module이 처리하는 값은 Module에 둡니다.
- 필드 수만 줄이려고 Model을 변수 저장소로 만들지 않습니다. Presenter의 얇은 전달 함수는 허용하며 클래스별 변경 이유와 책임을 기준으로 분리합니다.
- Presenter 하나를 상위 중재자로 보존하는 것을 우선하지 않습니다. 독립된 상태 수명 / 변경 이유 / 입력과 View 및 이벤트 조율이 있고 기존 클래스의 상태 / 분기 / 이벤트 책임을 실제로 줄이면 Presenter도 분리 후보입니다. 줄 수 감소나 단순 전달만을 위한 분리는 피하며 새 클래스와 책임 이전은 승인 후 적용합니다.
- 상위 Presenter는 하위 Presenter에 요청하고 이벤트로 결과를 받습니다. 하위 시스템이 특정 적 타입이나 상태 전환을 직접 제어하지 않도록 하며 이벤트 구독 자체를 양방향 의존으로 보지 않습니다.
- 동급 Presenter는 상호 의존 대신 공통 상위 중재자나 독립 기능으로 연결합니다. 다른 시스템의 Model을 직접 수정하지 않으며 Presenter 간 호출이라는 이유만으로 모듈로 전환하지 않습니다.
- 상위 계층은 하위의 성공 / 실패 계약을 신뢰하고 관계 / 설정 검사를 반복하지 않습니다. 실제 수명 / 콜백 재진입 / Unity 파괴 경계의 검사는 유지합니다.
- OnEnable / OnDisable과 새 등장 계약을 구분합니다. 활성화만으로 회차 상태나 게임 전체 이력을 초기화하지 않습니다. 상위 FSM 전환 / 행동 내부 판단 / 이동 실행의 경계를 유지하며 파일 길이를 줄이려고 로직을 통째로 옮기지 않습니다.
- 기존 Enemy의 상태 초기화 계약을 유지하고, 새 기능의 실제 필요와 반복이 확인되기 전에는 추상 클래스 / 인터페이스 / 공통 Data 계층을 추가하지 않습니다.
- 하나의 대형 Model 또는 Presenter에 독립 규칙을 몰아넣지 않고 기능별 모듈로 분리합니다. 모듈 내부의 MVP 분리 여부는 실제 필요에 따라 결정합니다.
- 콘텐츠는 독립 미니게임을 늘리기보다 핵심 업무 시스템을 공간별로 재사용합니다.
- 업무는 공간 간 이동을 유도하고, 멀티플레이에서 자연스러운 역할 분담과 긴급 지원을 만듭니다.
- 포식자는 대놓고 등장 / 몰래 등장 / 숨어 있음의 세 등장 방식과 공통 행동 뼈대를 공유할 수 있습니다.
- 각 포식자는 외형이나 수치가 아니라 고유한 문제 해결 규칙으로 구분합니다.
- 피해 복구는 가능한 한 기존 파티 준비 업무를 재사용합니다.

## TERMINOLOGY

- `Preparation`: 음식, 장식, 의상 등 종료 시 실제로 유효한 파티 준비 상태. Mission 달성 이력과 분리하며 음식 탈취나 배치 이탈로 현재 상태가 무너지면 평가에 반영
- `Safety`: 초대 NPC 토끼의 안전 상태
- `Mood`: 손님이 느끼는 즐거움과 편안함
- `Predator Control`: 포식자 문제 대응 성과
- `사전 신호`: 피해 전에 포식자 존재나 행동을 추론할 수 있는 시청각 또는 오브젝트 변화

- `The Exit 8`: 정상 상태 기억 / 미세한 변화 발견 / 공간과 오브젝트 변화로 존재 추론

## SYSTEM_BOUNDARY

- 공간의 환경 역할과 고유 약점은 `SPACE`, 업무의 입력·운반·배치 흐름은 `PARTY_PREPARATION`이 소유합니다.
- NPC 상태와 플레이어의 오인 행동 반응은 `NPC_RABBIT`, 최종 점수 계산은 `RESULT_EVALUATION`이 소유합니다.
- 포식자의 등장·징후·행동·성공·실패 규칙은 `PREDATOR`, 네트워크 동기화와 인원수 보정은 `MULTIPLAYER`가 소유합니다.
- 아이템·일반 월드 상호작용의 분리와 공통 상태·검증 경계는 `PLAYER_INTERACTION`, 변칙 사건의 규칙과 상태·발생·해결은 `ANOMALY`가 소유합니다.
- 제작에 필요한 모델 / 애니메이션 / 환경 / 오디오와 확보 우선순위는 `ASSET_REQUIREMENT`가 소유합니다.
- 시스템 공통 방향과 MVP 범위만 이 문서에서 관리합니다.

## SYSTEM_SCOPE

### MVP

- 네 핵심 공간 / NPC 토끼 약 8마리 / 기본 파티 준비 업무
- 조리 타이밍 / 물건 찾기·운반 / 테이블·장식·음식 배치 / 음악 / 의상 준비
- Mood / 파티 준비도 / 기본 결과 평가
- 제작 상황에 맞춘 포식자 최대 5종과 각 고유 대응 / 피해 복구
- 멀티플레이 핵심 동기화

### 확장

- 음료 별도 제작 / 액세서리 꾸미기 / 창고 정리 / 포식자 세부 행동 변형
- 클래스 상세 / 성장 트리 / 시설·장비 업그레이드 / 복잡한 제작

### 보류

- 대규모 전투 / HP 중심 생존 시스템 / 복잡한 NPC AI
- 클래스와 시설·장비 시스템의 MVP 포함 여부는 결정 전까지 보류합니다.
